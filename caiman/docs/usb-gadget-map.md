# Caiman USB2 device-mode register map

The stock path uses three distinct components: MAX77759 for Type-C attach and role, the I²C eUSB2 repeater plus Exynos PHY/link wrapper for USB2 signaling, and the Synopsys device controller for enumeration. The register sequence below reconstructs the Linux UTMI path. The exact cold-start clock transaction sequence and firmware ownership of DMA protection remain unresolved. Start by capturing the PMU/clock state and the controller ID at the handoff. A separate Pixel reboot driver supplies the Linux bootloader reboot reason. All findings are static.

Module citations use hexadecimal byte offsets from the named function in its ELF section. Where specified, ELF data offsets are section-relative. DT citations refer to `~/caiman-work/caiman-live.dts`. CAL source citations refer to the local `~/caiman-work/ref-acpm` files. Upstream citations use the source line numbers displayed by Code Browser.

## 1. Power, clocks, repeater and PHY

1. **Power HSI0.** The Linux enable order is vdd075, vdd33, vdd12, then the CAL power-domain operation and S2MPU resume callback. The supplies are S2MPG14 LDO8, LDO19, and LDO9 respectively. Use their board-configured voltage settings. Domain `0x0c` is CAL ID `0xb1380018`, with `need_smc=0x11010204`. The shipped `cmupmucal.ko` table `hsi0_on` at `.data+0x282c0` performs masked write `[0x15462a80] bit 0 = 1`, then waits for `[0x15462a84] bit 0 = 1`. `hsi0_status` at `.data+0x2ab10` reads that same status bit. These operations describe the PMU part of Linux's sequence. The CAL path also invokes secure restore when configured, followed by restoration of saved state. Verify access and ownership before using the PMU sequence in a loader. (DT:2962–2972, 8123–8131, 16620–16639, 16740–16748; `exynos_pd_hsi0_probe+0x48–0x88`, `exynos_pd_hsi0_ldo_manual_control+0x74–0x90`, `exynos_pd_power_on+0x94–0xd4`, `exynos_pd_probe+0x118`, `cal-if.c:231–249`, `pmucal_local_enable+0x90,+0x15c,+0x184`.)
2. **Establish the clock tree.** DT clock provider `0x0d` is at `0x26040000`; local HSI0 CMU is at `0x11000000`. The IDs are `0x22f GATE_USB32DRD_LINK` (aclk), `0x227 MUX_HSI0_USB20_REF` (sclk/phy_ref), and `0x43 VDOUT_CLK_TOP_HSI0_NOC` (bus). The top HSI0 NOC path has mux/divider/gate offsets `0x1094/0x188c/0x20bc` in CMU_TOP. At the local CMU, inspect muxes `+0x1000/+0x1004/+0x1008`, dividers `+0x1800/+0x1804/+0x1808/+0x180c`, and link ACLK `+0x20a4`, wrapper PCLK `+0x20a0`, eUSB control PCLK `+0x20b8`, eUSB APB `+0x20d8`, eUSB reset synchronizer clock `+0x2090`, eUSB reference `+0x20dc`, suspend clock `+0x20e4`, and controller REF_CLK_40 `+0x20ac`. The reference mux selects PLL divider (0) or TCXO user clock (1), with mux busy at bit 16. CAL describes gate control/status fields at bits 20, 21 and 28. The shipped clock driver registers the HSI0 hardware clock list, including `0x227` at `.data+0x610` and `0x22f` at `.data+0x7d0`. Linux uses managed clock enables and a separate bus rate vote. (`clk_exynos_gs.ko:zuma_clock_probe+0x148`.) The listed registers identify the relevant clock path, but a verified set of mux/divider/gate writes for an off-at-handoff Caiman has not been recovered. In particular, clock IDs are provider indices. (DT:8270–8291, 8325–8340, 15262–15268; `zuma-clock.h:27–44,91–102`; `zuma-cmucal-node.c:901–915,1442–1444,2709–2712,2750–2766`; `zuma-cmucal-sfr.c:17,149,207–209,446,527–535,855,1532–1551,1589–1605,4645–4650,8409–8411,8523–8540`; `dwc3_exynos_runtime_resume+0x54–0x78`, `dwc3_exynos_set_bus_clock+0x50`, `exynos_usbdrd_utmi_init+0x5c`.)
3. **Configure the repeater.** It is 7-bit address `0x3e` on HSI2C9 at `0x10c90000`, separate from the TCPC at `0x25`. The repeater's input pin state is `gph1-0`, function 0, no pull, and its VDD33 supply is LDO19. Linux selects that pin state during probe. With the rail and bus ready, read/modify/write register `0xb2` to clear bit 6, then read back. Next Linux reads `0x50` and iterates the DT tuples with `new=(old & ~(mask<<shift)) | ((value & mask)<<shift)`, writing and reading each byte. For this DT, shift=0 and mask=0xff in every row, so the ordered writes are `50:0a, 70:7c, 71:3c, 72:92, 73:83, 77:00, 78:0b, 79:60` (all hex). Linux explicitly programs enable and tuning. Static evidence supplies no register reset defaults or proof that either HS or FS works at defaults. Treat repeater configuration as required for a reproducible cold start and check the programmed state on a firmware handoff. (DT:4688–4695,6485–6503,6608–6632,6675–6684,8077–8121; `eusb_repeater_probe+0x284,+0x574–0x5b4`, `eusb_repeater_ctrl+0x2c–0x8c`, `eusb_repeater_power_on+0x3c–0x58,+0xe0–0x15c`.)
4. **Release USB2 isolation and enable UTMI clocks.** Linux calls repeater power-on, de-isolates, enables clocks, initializes the link wrapper, applies a DT tune staging pass, then initiates the eUSB PHY. The USB2 PMU register is `0x15463eb0`; `pmu_mask=<0>` denotes bit number zero. De-isolation is masked set of bit 0. The module uses the firmware-mediated `rmw_priv_reg` helper for this access. `0x15463eb4` is the separate DP isolation resource. Keep the domain/interconnect prerequisites up through the entire sequence. (DT:8325–8340,15436–15439; `exynos_usbdrd_utmi_init+0x18–0xd0`, `exynos_usbdrd_phy_probe+0x5c0–0x628,+0x924–0x940`, `exynos_usbdrd_utmi_phy_isol+0x14–0x5c`, `rmw_priv_reg+0x14–0x54`.)

The module's resource mappings and PHY info construction identify these banks. The PHY version low nibble is 1, and the 19.2 MHz rate maps to selector 1. The first eUSB jump-table byte `0x57` at `.rodata+0x32c` sends selector 1 to instruction `0x4380`, selecting the pre-rev-2 branch. ## 2. Session and Exynos glue

- **Physical attach.** Keep the port as a Type-C sink/UFP and wait for confirmed partner attach with VBUS present. DT connects PHY, UDC and repeater to extcon phandle `0x413` on MAX77759. The TCPC role path updates the data path, reports attachment to USB power supply, then propagates extcon state. The MAX77759 and shim VBUS getters read TCPC POWER_STATUS at `0x1e`. The MAX77759 path examines bit 3 (VBUS present) and can also read the 10-bit voltage field from `0x70`, in 25 mV units. These reads are independent of VBUS source control. Charger and USB power-supply policy are not DWC3 session registers. A complete MAX77759 cold-start configuration was not recovered here. (DT:6485–6507,6682–6683,8292–8294,8361–8363; `max77759_usb_set_role+0xb0–0xc4,+0x198`, `max77759_get_vbus+0x28–0x48,+0xb4–0xcc`, `max77759_set_vbus`, `google_tcpci_shim_get_vbus+0x58–0x5c`, `google_tcpci_shim_set_vbus`.)
- **USB2 wrapper override.** The PHY parser reads `is_not_vbus_pad`. The link initializer sets `0x11100010[1:0]=3` unconditionally. The PHY's pull-up helper clears/replaces those same two bits from its argument. This is the observed USB2 hardware override/control path. The same offset and mask in upstream Exynos2200 support are FORCE_BVALID (bit 0) and FORCE_VBUSVALID (bit 1). These names are a cross-SoC inference for Caiman, while the actual mask comes from the Caiman module. [Upstream phy-exynos5-usbdrd.c:43–45,1330–1333](https://codebrowser.dev/linux/linux/drivers/phy/samsung/phy-exynos5-usbdrd.c.html#43). The analysis recovered no HSI0 SYSREG BVALID/IDDIG override write from these modules. `0x11020000` is the syscon in DT; avoid extrapolating its bit layout from older Exynos integrations. Use forced peripheral GCTL role plus PHYCON controls. (`exynos_usbdrd_get_phyinfo+0xec–0x130`, `exynos_usbcon_init_link+0x98–0xac`, `exynos_usbdrd_utmi_set+0x30–0x38`, `exynos_usbcon_dp_pullup_en+0x18–0x34`; DT:8071–8075,8280–8285,8353–8356.)
- **Software session.** The device-role callback tunes the PHY, runs the Exynos core-quirk setup, calls `usb_udc_vbus_handler(gadget, true)`, then `usb_gadget_connect`. The last two are software notification and gadget connect, respectively. It then sets `GCTL[13:12]=2` (device role); set device role before gadget setup in a standalone implementation. The disconnect branch calls VBUS false and gadget disconnect. (`dwc3_otg_start_gadget+0x15c–0x1a8,+0x1c8–0x1d0`; [DWC3 core.h:248–280](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#248).)
- **Core quirks.** `dwc3_exynos_core_init` uses the DWC3 global mapping starting at physical `0x1121c100`. The common path ORs GSBUSCFG0 with `0x22220009` (older DWC3 revisions below 2.20a use `0x9`), sets GUCTL bit 14 with conditional extra fields, and modifies relevant GUSB2PHYCFG/GCTL fields. The DWC_usb31 branches have additional revision-dependent writes, so apply a branch only after identifying the core. The DWC_usb31 1.70a branch compares family `0x3331` and revision `0x3137302a`, then writes GSBUSCFG1 bit 11, GUCTL upper field `0x03c00000`, plus ORs `+0xd024` with `0x000b8400` and `+0xd020` with `0x0d900000`, both offsets relative to `0x11210000`. The same binary also handles `0x5533` DWC_usb3. Those constants describe driver support and leave the actually fitted ID unverified. Capture GSNPSID and VER_NUMBER/VER_TYPE first. (`dwc3_exynos_core_init+0x60–0x1b0,+0x2ac–0x408,+0x4ac–0x4e0`; [DWC3 core.h:86–142,1298–1305](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#1298).)

## 3. DWC3 EP0-only device

All DWC3 offsets below are relative to physical `0x11210000`. Use aligned little-endian 32-bit MMIO and bounded waits. EP0 OUT is physical endpoint 0 and EP0 IN is physical endpoint 1.

1. **Quiesce and reset.** Read GSNPSID `+0xc120` and hardware parameters `+0xc140..0xc15c`, plus DWC_usb31/32 version words `+0xc1a0/+0xc1a4` when the family calls for them. Preserve active inherited DMA mappings until the old controller is halted. Clear DCTL.RUN_STOP (bit 31 at `+0xc704`) and wait for DSTS.DEVCTRLHLT (bit 22 at `+0xc70c`), draining pending events if the old ring is owned and accessible. Use the device-side soft reset `DCTL.CSFTRST=1` (bit 30) and wait for self-clear. Upstream uses revision-specific delays, including a post-reset delay on older DWC_usb31. Set `GCTL[13:12]=2` at `+0xc110`. Keep `GUSB2PHYCFG(0)` at `+0xc200` awake during bring-up with SUSPHY (bit 6) and ENBLSLPM (bit 8) clear. Apply DT's free-clock quirk by clearing bit 30. Preserve the hardware-selected UTMI interface width/turnaround unless verified for this integration. Start with USB2 LPM disabled and leave PIPE configuration to the identified revision. [DWC3 core.c:318–375](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.c.html#318) · [DWC3 gadget.c:2617–2787](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.c.html#2617) · [DWC3 core.h:248–330](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#248) · DT:8313–8319.
2. **Program DMA and speed.** Allocate a coherent or explicitly synchronized event buffer (e.g. 4096 bytes), aligned TRBs (16 bytes each), and separate setup/reply buffers. Program device-visible address low/high at `+0xc400/+0xc404` and byte length at `+0xc408`. Acknowledge any stale count by writing the observed byte count (mask `0xfffc`) back to `+0xc40c` and initialize the software cursor to zero. Configure `DCFG +0xc700`: clear address bits 9:3 and LPM_CAP bit 22, set bits 2:0 to `0` for HS or `1` for forced FS. For a minimal device event set, `DEVTEN +0xc708=0x7` enables disconnect/reset/connect-done. Use ordered DMA publication, clean cached descriptors and IN data before handing them over, and synchronize/invalidate setup and event bytes before CPU consumption. [DWC3 core.c:500–583](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.c.html#500) · [DWC3 core.h:147–171,430–445,495–535](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#147) · [DWC3 gadget.c:2560–2614](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.c.html#2560).
3. **Configure EP0.** At endpoint base `0xc800+0x10*n` write PAR2/PAR1/PAR0 at `+0/+4/+8`, then command at `+0xc`. Poll CMDACT (bit 10) clear, then require status bits 15:12 zero. Issue DEPSTARTCFG (`0x409`, resource index 0) on OUT with zero parameters. For each direction issue DEPCFG (`0x401`), PAR2=0, PAR1=`0x500|(n<<25)` (interrupt 0, completion and not-ready), PAR0=`0x200` (control, 64 bytes, FIFO 0, INIT). Issue DEPXFERCFG (`0x402`) per direction with PAR0=1 and other params zero. Set `DALEPENA +0xc720=3` for EP0 only. Initial MPS 64 is the proposed HS/FS-only default; upstream starts with its SS default then modifies on connect-done. [DWC3 gadget.c:541–650,2913–3001](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.c.html#541) · [DWC3 gadget.h:22–49](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.h.html#22) · [DWC3 core.h:567–593](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#567).
4. **Arm SETUP, then connect.** A single OUT setup TRB is `[setup_dma_lo, setup_dma_hi, 8, 0xc23]`, including HWO, LST, ISP_IMI, IOC and CONTROL_SETUP. STARTTRANSFER (`0x406`) uses PAR0=TRB address high, PAR1=low, PAR2=0. After command completion record the returned resource index (bits 22:16). Set RUN_STOP after the ring and first setup are ready and check that DEVCTRLHLT drops. Maintain one control transfer at a time. [DWC3 ep0.c:35–102,280–293](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/ep0.c.html#35) · [DWC3 core.h:856–889](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#856) · [DWC3 gadget.c:2617–2690,2771–2787](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.c.html#2617).
5. **Service events.** Count is in bytes. Consume 4-byte events modulo the ring and acknowledge the consumed byte count by writing it to GEVNTCOUNT. Endpoint events have bit 0 clear, endpoint in bits 5:1, and event type in bits 9:6 (transfer complete 1, not-ready 3). For ordinary device events bit 0 is set, bits 7:1 are zero, and event type is in bits 11:8 (disconnect 0, reset 1, connect-done 2). On reset clear DCFG address and reset software configuration/state. Cancel stale data/status phases and return to a single armed SETUP, respecting the hardware-owned transfer and its resource index. On connect-done read `DSTS[2:0]` (HS 0, FS 1), retain 64-byte max packet for either, and issue DEPCFG MODIFY (`PAR0=0x80000200`, other params as above) without reallocating resources. On disconnect discard pending reboot state. [DWC3 core.h:78–82,1439–1528](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/core.h.html#1439) · [DWC3 gadget.c:4050–4311,4510–4640](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/gadget.c.html#4050).
6. **Serve EP0.** On setup completion, decode the 8-byte request. Provide device and configuration descriptors with one class-`0xff` interface and zero non-control endpoints (18 bytes total for the configuration and interface). Advertise EP0 max packet 64 and use a VID/PID assigned for the project. Serve USB2 qualifier/other-speed descriptors if exposing both speeds, plus requested advertised strings, GET_STATUS, GET_CONFIGURATION, SET_CONFIGURATION and alt-setting zero if queried. Bound descriptor replies to `wLength`, including a ZLP if a shorter reply ends on a packet boundary. For SET_ADDRESS follow the controller-specific order in upstream `dwc3_ep0_set_address`: validate range/state and write DCFG before scheduling status. Start an IN data stage promptly with CONTROL_DATA (type 5); wait for the status not-ready event, then use zero-length CONTROL_STATUS3 (type 4) in the opposite direction. For no-data commands wait for status not-ready on IN and start CONTROL_STATUS2 (type 3). Re-arm SETUP after status completes. For unsupported or malformed requests stall and restart SETUP. Handle a replacement SETUP during an unfinished transfer using the TRB SETUP_PENDING status and the upstream status/cleanup path. [DWC3 ep0.c:146–188,228–253,598–630,792–866,876–976,980–1180](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/ep0.c.html#146).
7. **Vendor command design.** An example contract is device-recipient vendor OUT `bmRequestType=0x40, bRequest=0x01, wValue=0, wIndex=0, wLength=0`, accepted only in configured state and when the local reboot function is enabled. Latch intent at SETUP, send status IN, and schedule the existing platform reboot-to-bootloader path after successful status completion. Cancel the intent on a replacement SETUP, reset, or disconnect before status completion. The local loader’s `reboot()` and fastboot-like server request EFI cold reset. Its USB server uses firmware protocols. Use the Pixel reboot reason below for the vendor request. [DWC3 ep0.c:826–864,920–977](https://codebrowser.dev/linux/linux/drivers/usb/dwc3/ep0.c.html#826) · `hakios-xnu-kernel/xnuloader/loader.c:594–600,3654–3682,3998–4001`.

**Stock Pixel reboot reason.** The additional shipped `pixel-reboot.ko` maps the literal `bootloader` to `0xfc`. Use the stock bootloader reason path after the status IN completion, followed by the platform restart. In Linux, the notifier writes reason `0xfc` to physical `0x15460810` through `set_priv_reg`, then on success records `0x800000fc` under the GBMS tag `RSBM` (`0x5253424d`). The Linux helper uses privileged firmware service `0x82000504`, write selector 1. The restart handler in this module only logs, so a separate platform reset is still required. This identifies the Linux-side interface and value. The static inputs leave firmware permission from a standalone loader and ABL dependence on the GBMS mirror unverified. (DT:15374–15379,15436–15439; `pixel_reboot_probe+0x50–0x114,+0x13c–0x14c`, `pixel_reboot_handler+0x84–0x88,+0x1a8–0x1ac,+0x1fc–0x23c`, `pixel_restart_handler+0x10–0x1c`, `set_priv_reg+0x18–0x54`.)

### DMA translation and protection

- **SYSMMU is in the DT path.** The DWC3 child points to `0xd5` (Samsung SYSMMU v9 at `0x11040000`, secure companion at `0x11050000`, default stream encoding `0x108`). The Linux disable routine clears bit 0 on the configured context/VM control registers and also clears context configuration and invalidates. It is not a warrant to indiscriminately disable the HSI0 IOMMU. For a bare-metal driver, physical RAM addresses are valid only if an authorized pass-through context is established and verified. Otherwise provision mappings for the actual USB stream and use the mapped bus addresses. This applies to both event writes and TRB/data reads and writes. (DT:1231–1243,8296–8310; `samsung_iommu_v9.ko:__sysmmu_disable+0x1c–0x80,+0xa0–0xdc`, `__sysmmu_enable`.)
- **S2MPU is independent.** DT associates the PHY with HSI0 S2MPU v9 at `0x11070000`. Linux calls the registered S2MPU PM callback after HSI0 power-on. DT bootargs name protected modules. An identity map at the SYSMMU does not establish access through S2MPU. Use an owned, DMA-permitted region. The advertised memory regions are named xHCI pools and marked `no-map`: `0x17bc0000+0x40000`, `0x97000000+0x400000`, and `0x17bb5000+0xb000`. Those reservations and the DMA window describe Linux configuration and give no permission or ownership to a new loader. (DT:1556–1575,5501–5506,8299–8305,8341,15169; `exynos_pd_power_on+0xd4`, `exynos_usbdrd_s2mpu_manual_control+0x44–0x78`.)

## 4. Handoff and read-only inspection

**Guess, normal boot:** ABL may leave the domain gated, PHY isolated, or controller stopped, even if the TCPC retains a sink attach. **Guess, fastboot:** while serving USB, ABL likely has clocks, PHY, repeater and DMA working. A transition out of fastboot may tear any of them down or leave active endpoints/ring pointers into firmware-owned memory. The supplied modules describe Linux bring-up and teardown and cannot establish either ABL handoff. The existing local loader's EFI USB-protocol call is separate evidence of a firmware-assisted path only.
