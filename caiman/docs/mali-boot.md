# Mali-G715 CSF cold boot on caiman

Static analysis of the supplied r54p3 modules and firmware. Citations are hexadecimal byte offsets from symbols in `mali_kbase.ko` unless prefixed with `mali_pixel.ko`. Register offsets are relative to GPU MMIO at `0x1f000000` unless identified otherwise. Values from the live DT, saved probe log, supplied Android log notes, and firmware bytes are identified separately. **GUESS** marks an inference about hardware or runtime behavior that the inputs cannot demonstrate.

## 1. Fault decode

| Register | Exception | Access | Source ID on arch 11 |
|---|---|---|---|
| GPU_FAULTSTATUS `0x6e000e80` | `0x80`, `GPU_BUS_FAULT`. Bit 10 is set, so kbase's bus-fault formatter reports PA_VALID true. | Bits [9:8] = 2, `READ`. See formatter caveat below. | `0x6e00`, core ID `0x37` = MMU, uTLB bit 0, internal requester 0 (`Not used`). |
| AS0 FAULTSTATUS `0x7cd002c0` | `0xc0`, `TRANSLATION_FAULT at level 0`. | Bits [9:8] = 2, `READ`. | `0x7cd0`, core ID `0x3e` = Command Stream Frontend, uTLB bit 0, internal requester `0xd` = `mcu`. |

The GPU bus-fault path extracts exception [7:0], access [9:8], source [31:16], core ID [31:25], and uTLB [24] at `kbase_gpu_report_bus_fault_and_kill+0x44..+0x88,+0xdc..+0xf0`. Its call at `+0x90` passes the already-extracted access value to `kbase_gpu_access_type_name`, which extracts [9:8] a second time. That formatter can therefore print `ATOMIC` alongside numeric access 2. The actual decoder table maps 2 to `READ`. The AS0 reporting path passes the raw status to that helper at `kbase_mmu_report_mcu_as_fault_and_reset+0x38..+0x60,+0xa4..+0xb4`. The exception jump table at `kbase_gpu_exception_name+0xc..+0x28` lands at `+0x14c` and `+0x17c` respectively. The access table is referenced at `kbase_gpu_access_type_name+0x0..+0xc`.

For these source IDs, the old-format path extracts requester [7:4] at `fault_source_id_internal_requester_get+0x0..+0x14`. The arch-11 description table at `.rodata+0x19820` contains the MMU and CSF entries at `+0x250` and `+0x2b0` from the table start (`fault_source_id_core_type_description_get+0x1c..+0x28`, `decode_fault_source_core_id_t_desc+0xdc..+0x128`). The requester paths are `fault_source_id_internal_requester_get_str+0x124..+0x138,+0x1cc..+0x23c` and `decode_fault_source_csf_r_t+0xec..+0x120,+0x174..+0x17c` (arch-11 jump table, relocation at `.rodata+0x1b8e0`).

The saved probe log puts the valid PA `0xf000003f` inside the first 64 bytes of the root page at `0xf0000000`, and the AS0 fault VA is zero. **GUESS:** an MMU root-table read failed on the fabric, with the MCU's VA-zero read subsequently reporting a failed level-0 translation. The PA ending in `0x3f` is consistent with a cache-line transaction. The fault pair identifies the consumers and the walk level. It does not identify the responding interconnect block or establish whether the root descriptor was consumed.

## 2. Cold boot sequence, registers, and descriptors

The sequence below covers the traced cold firmware path and its relevant PM branches. Register enum IDs are converted through the v11 map and its inherited map. Conditional reset, PM-domain, and quirk branches are called out because the supplied log does not record their runtime selection. The first-time firmware entry acquires a PM active reference before calling the loader (`kbase_device_firmware_init_once+0x44..+0x4c`).

**Conditional quirk writes.** The hardware init writer restores cached words to `0xf04,0xf08,0xf0c,0xf00` if their register IDs are valid, using device structure words at offsets `0,4,8,0xc` respectively. The initialization branch obtains overrides from DT and derives defaults from register readback plus feature and issue bits. For example, the first cached word can gain bit 29 and bit 17, and the second can gain bit 0. The provided logs lack these register readbacks, so exact Android write values for this branch are unresolved. The separate IDs `0x167` and `0x168` are outside the v11 map, so their newer-register writes are not part of this arch-11 list. (`kbase_pm_init_hw+0x274..+0x314,+0x35c..+0x4e0,+0x594..+0x5cc`, `kbase_regmap_v10_8_init+0x1330..+0x135c`, `kbase_regmap_v11_init+0x24..+0x34`.)

**AS values.** `kbase_mmu_get_as_setup+0x0..+0x20` builds TRANSTAB from the stored PGD physical base, MEMATTR = `0x00084c8d888d8f88` (slots 0–7 are `88 8f 8d 88 8d 4c 08 00`), and base TRANSCFG = `6`. `kbase_mmu_hw_configure+0x14..+0x44` merges `0x42000000` in noncoherent mode, resulting in `0x42000006` for this setup. The other branch clears the mode/shareability fields with `~0x73000000` and ORs `0x62000000`, resulting in `0x62000006` from the same base. The probe's `0x410001c6` differs in [25:24] and includes an extra `0x1c0` that kbase's AS setup does not add. **GUESS:** interpreting the hardware names, this is AArch64 4K with write-back walk attributes and read allocation on the kbase noncoherent path. The byte values and bit positions above are the binary evidence.

**Descriptor layout.** `entry_set_pte+0x0..+0x8` replaces all 12 low address bits with `0x403` for intermediate table pointers. `entry_set_ate+0x0..+0x9c` combines the aligned PA with AF (bit 10), descriptor type 1 for a block and **type 3 for a level-3 leaf**, index in bits [4:2] from flags [18:16], AP in [7:6], SH in [9:8], and XN at bit 54. Flags bit 2 selects AP `01` (writable); otherwise flag bit 14 selects AP `11` (read-only); absent both the field is zero. Flags bit 10 selects SH `10`, otherwise flag bit 9 selects SH `11`, otherwise SH is zero. Flags bit 3 supplies XN. The constructor leaves bits 11 and 53 clear. `ate_is_valid+0x0..+0x14`, `pte_is_valid+0x0..+0x10`, and `entries_invalidate+0x0..+0x10` confirm the descriptor type tests and zero invalid entries. kbase carries a software entry count in [58:55] of the first three entries (`set_num_valid_entries+0x8..+0x2c`).

For this blob on the noncoherent branch, flags `0x09/0x0d/0x8000000b/0x80000009` select index 0 and SH 0. The shared section flags `0xc000001b` select index 5 and SH 0 after the cache-mode fallback. Thus the ordinary non-executable RO sections use low bits `0x4c3` plus bit 54, ordinary executable RO pages use `0x4c3`, ordinary RW pages use `0x443` plus bit 54, and shared RW pages use `0x457` plus bit 54. This follows the flag conversion and MEMATTR selection at `kbase_csf_firmware_load_init+0x71c..+0x7d8` and assumes the MGM transformation for group zero below.

**GLB interface.** After the first IRQ, read shared VA `0x04000000` words at offsets `0,4,8,0xc,0x10,0x14` for interface version, features, input VA, output VA, CSG count, and stride. kbase rejects a zero version and checks that the input and output VAs lie inside the shared mapping before installing their host pointers. Later global IRQ handling compares GLB_REQ and GLB_ACK at offset zero in their respective pages. Global initialization follows capability parsing. The separate `kbase_csf_firmware_enable_mcu` path adjusts GLB input at offset zero before writing AUTO on later starts. The cold boot helper writes AUTO directly. (`parse_capabilities+0x30..+0xdc`, `kbase_csf_interrupt+0x1060..+0x1080`, `kbase_csf_firmware_load_init+0xc18..+0xc78`, `kbase_csf_firmware_enable_mcu+0x34..+0x78`.)

## 3. Protected firmware section

The blob's protected interface section spans VA `0x03000000..0x03040000` (64 4 KiB pages, 256 KiB, flags `0x2b`). Bit 5 selects the protected allocator. kbase initializes the DT-backed allocator and obtains physical pages via its callbacks, then runs the section copy and installs the resulting pages in the firmware MMU. This matches the supplied Android allocation note. (`kbase_csf_protected_memory_init+0x0..+0x190`, `kbase_csf_protected_memory_alloc+0xf0,+0x120`, `kbase_csf_firmware_load_init+0x5e8..+0x68c,+0x94c`.)

If protected allocation returns null, the loader warns that firmware protected mode entry will be unsupported, terminates the protected-memory interface, frees the temporary page array and advances to the next firmware entry. It still reaches the normal cold-start path. This is a supported nonprotected boot path in the module. Static analysis cannot establish whether this particular firmware reaches first GLB IRQ on a particular bare-metal platform state. The observed fault VA is zero and therefore outside the omitted PROT range. (`kbase_csf_firmware_load_init+0x65c,+0xad4..+0xafc,+0xbb8..+0xc18`, `.rodata+0xad5`; saved probe log.)

## 4. Pixel-specific pre-start work

- **Power SMC.** Pixel top power-on uses function ID `0x82002010` with `x1=0, x2=12, x3=1` and remaining argument registers zero. Power-off uses the same ID with `x3=0`. The return value is checked. The module also has generic SMC wrappers that dispatch a supplied ID, or assemble one from arguments, and do not establish a second fixed cold-boot ID. The Pixel hard-reset callback reuses the top power calls. (`gpu_pm_power_on_top_nolock+0xcc..+0x108`, `gpu_pm_power_off_top_nolock+0x6c..+0xa8`, `gpu_pm_hw_reset+0x9c..+0xa4`, `invoke_smc_fid+0x0`, `kbase_invoke_smc+0xc..+0x34`.)
- **S2MPU.** `gpu_pixel_init+0x44` calls `gpu_s2mpu_init`. The latter resolves the `s2mpus` phandle, finds the platform device and emits the success message. This function does not program a protection window or issue an SMC. The DT binds `0x1ee70000` to `google,s2mpu-v9` on the top domain. The configured message establishes device lookup, and probe CTRL0 readback is an observation. The supplied GPU modules do not establish the S2MPU hardware's effective access policy or rule out other fabric access restrictions. (`gpu_s2mpu_init+0x38..+0x68,+0x98..+0xbc`; DT S2MPU and Mali nodes.)
- **MGM and SLC.** Firmware insertion passes group zero. Pixel MGM clears PBHA for groups zero and three, installs the SLC partition PBHA for group one, and leaves group two's entry alone. PBHA is bits [62:59]. Thus the ordinary cold firmware leaves can use zero PBHA without allocating an SLC partition for them. kbase's L2 setup has a feature/device-gated PBHA register path, with eight cached settings words at `0x340..0x35c` on the v11 map. The extra nonzero-PBHA branch replaces one byte at `0x320 + 4*(pbha >> 2)` with `0x11`, shifted by `8*(pbha & 3)`. (`kbase_csf_firmware_load_init+0x930..+0x94c`, `kbase_mmu_create_ate+0x60..+0xa8`, `mali_pixel.ko: mgm_update_gpu_pte+0xc..+0x48, slc_wipe_pbha+0x0, slc_set_pbha+0x0..+0x10`, `kbase_pbha_write_settings+0x0..+0xec`, `kbase_regmap_v11_init+0x170..+0x1fc`.)
- **AXI and QoS.** Top power-on calls the DVFS power event before the SMC. The QoS setter requests a BTS scenario through `bts_add_scenario` / `bts_del_scenario`; DT supplies `g3d_performance` and threshold `0x61a80`. The init hardware path includes optional DT quirks and a newer-feature `mac-step-cycles` register RMW. The supplied Mali node has no explicit quirk or MAC-step values. The called BTS implementation and its AXI register writes are outside these two binaries. **GUESS:** these calls are part of normal platform performance setup, with no evidence here that the BTS vote is necessary for the first AS0 fetch. (`gpu_pm_power_on_top_nolock+0xa8`, `gpu_dvfs_qos_set+0xb4,+0xc8`, `kbase_pm_init_hw+0x1e0..+0x314,+0x35c..+0x38c`.)
- **Pixel firmware config.** `platform_funcs+0x48` relocates to `gpu_fw_cfg_init`. The hook writes zero to the option named `Log verbosity`; this blob's type-1 entry at file offset `0x114` sets its firmware VA to `0x004114bc`. A lookup failure produces a warning and the hook returns success. The other type-1 option is `WA_CFG0` at VA `0x00410000`; workaround writes are driven by `quirks-ext` or `quirks_ext`, which are absent from the supplied node. (`kbasep_platform_fw_config_init+0xc..+0x38`, `gpu_fw_cfg_init+0x10..+0x44`, `gpu_sscd_fw_log_init+0x24..+0x54`, `kbase_csf_firmware_cfg_fw_wa_init+0x20..+0x50`, `kbase_csf_firmware_cfg_fw_wa_enable+0x44..+0x78`; firmware entries and DT.)
- **Other pre-start shared-memory patches.** Initialize the firmware page-fault-counter pointer at VA `0x00410408` (type 8, file offset `0x310`), using the designated counter backing VA with low bits `0xffc`, and zero the backing word. Trace entries at file offsets `0x14c..0x28c` describe `fwutf`, `firmware trace`, `fwlog`, `benchmark`, `timeline`, `debug monitor in`, `debug monitor out` and `gpu_metrics`. The trace initializer maps backing data and counter pages and patches the descriptor-supplied firmware addresses with data VA, insert/extract counter VAs, byte size and enable words. The first four patch addresses are successive words for most entries, with separate mask addresses in several entries. These operations precede AS0 UPDATE. (`init_page_fault_cnt_firmware_memory+0x18..+0x50`, `kbase_csf_firmware_load_init+0x504..+0x514,+0xbc4..+0xc08`, `kbase_csf_firmware_trace_buffers_init+0x58..+0x1ac`; blob data.)

## 5. Concrete changes to gpu.c

1. **Match the root walk first.** In `pte_of()` emit `next | 0x403` for table pointers. In `gpu_firmware()` program `TRANSCFG=0x42000006`, `TRANSTAB=root`, and `MEMATTR=0x00084c8d888d8f88` in that order, low word then high word. Poll AS_STATUS before and after UPDATE. Keep the producer barrier before the MMIO publication. These changes address the earliest differences on the faulting path. (`entry_set_pte+0x0..+0x8`, `kbase_mmu_get_as_setup+0x0..+0x20`, `kbase_mmu_hw_configure+0x14..+0xec`.)
2. **Match leaf attributes.** In `map_pages()` retain type 3 and AF, drop bit 11 and bit 53, use bit 54 alone for XN, and use the AP, SH and MEMATTR formulas in §2. Apply the profile to every section, including shared memory. Print the four descriptor values for VA zero and the readbacks of the three AS0 registers before starting. (`entry_set_ate+0x0..+0x9c`, `kbase_csf_firmware_load_init+0x71c..+0x7d8`.)
3. **Apply L2 settings while L2 is off.** After reset and before the first L2 power-on, set the DT ASN hash words at `0x2c0..0x2c8`, set L2_CONFIG bit 24, and read back the result against Android's `0x01140000`. Program noncoherent mode before the PM power-up stage as kbase does. Use the 64-bit mask register pairs for power control and wait for L2 ready. A mandatory all-shader-ready gate before MCU start is unsupported by the cold loader. (`kbase_pm_init_hw+0x318..+0x328`, `kbase_pm_l2_update_state+0x608..+0x660,+0x784..+0x7a0`, `kbase_csf_firmware_load_init+0xbf0`.)
4. **Mirror the nonprotected loader and cold-boot signal.** Continue to skip PROT when there is no protected allocator. Implement the pre-start shared-memory patches in §4 for parity, including writing `Log verbosity=0`. Clear stale JOB and MMU status before starting, then issue MCU_CONTROL `2`. For polling, use raw JOB bit 31, clear it after capturing it and verify the GLB header and page bounds. Treat status 1 as a diagnostic and record both halves of GPU_FAULTADDRESS on failure. If later doing the GLB protocol, use the input/output pages advertised by the header. (`kbase_csf_firmware_load_init+0xad4..+0xafc,+0xbc4..+0xc18`, `boot_csf_firmware+0x8c..+0x180`, `kbase_csf_interrupt+0xf4..+0x10c,+0x1034..+0x1044`, `parse_capabilities+0x30..+0xdc`.)
5. **Isolate the PA issue if the root still faults.** **GUESS:** if the same bus fault persists with the matching root descriptor and TRANSCFG, compare against a separately established GPU-visible, reserved DRAM allocation. Changing only the table/firmware pool and recording the new 64-bit fault address distinguishes a repeatable pool-dependent failure from later firmware initialization. The historical log puts the fault in the `0xf0000000` root line, while the current source defaults to `0xd0000000`; the latter is not a verified successful boot. Leave the S2MPU register dump observational. Its effective policy lies outside `gpu_s2mpu_init+0x38..+0xbc`, and a CTRL0 write cannot substitute for establishing which PA range the GPU can read. No outcome on hardware is claimed.
