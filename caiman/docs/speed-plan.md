# Caiman speed investigation and plan

Static investigation only; no build, device access, or performance measurements were performed. Paths below are relative to `~/caiman-work/hakios-xnu-kernel` (K), the caiman repository containing this document (P), or `~/caiman-work` (W). Line numbers refer to the existing files before this patch.

## 1. Display

The run reports window 5 on DPP 0, BGRA8888 at physical 0xfac00000, 1280×2856 and 5120 bytes/row (W/darwin-touch1.txt:1300–1310). A full destination pass writes 14,622,720 bytes (13.95 MiB), plus source reads; this is arithmetic on those logged dimensions. The loader hands that physical address, rowbytes and dimensions to XNU (P/probe/xnu.c:724–730); console initialization maps it and the framebuffer driver takes `vinfo.v_baseaddr` (K/xnu-src/xnu-8796.121.2/osfmk/console/video_console.c:2837–2843, 2874–2881; K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:602–605). The source is each retained IOSurface's pixels, with its stride and source/destination rectangles, not necessarily a single whole-screen memcpy; unscaled rows use memcpy, scaled rows sample each pixel, and every supplied layer is drawn (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:830–843, 846–899, 1073–1100, 1170–1187, 1499–1543). The run reports logical 1125×2436 on the larger panel, so scaling is relevant (W/darwin-touch1.txt:1423).

The console uses `ml_io_map_unmappable`, with WCOMB when `HAS_UCNORMAL_MEM` or `BCM2837` is defined and IO otherwise (K/xnu-src/xnu-8796.121.2/osfmk/console/video_console.c:2856–2879); the generic patch defines BCM2837 and generic PSCI SMP (K/xnu/hakios.patch:3389; inspect the adjacent configuration for the actual build). **The effective build macro and runtime page attributes have not been verified**, so do not assume WCOMB. Ordinary `ml_io_map` is IO and `ml_io_map_wcomb` explicitly requests WCOMB (K/xnu-src/xnu-8796.121.2/osfmk/arm64/machine_routines.c:1649–1676). There is no per-frame `dc cvac` in the drawing path (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:830–899, 1499–1565). A cached mapping of the scanout is not interchangeable with WCOMB: aliases, cache-line ownership, DMA visibility and ordering must be established first; cleaning a separate cached shadow does not make DECON read that shadow because its programmed base remains 0xfac00000 (W/darwin-touch1.txt:1305; K/xnu-src/xnu-8796.121.2/osfmk/console/video_console.c:2837–2879).

Command mode was idle with masked hardware trigger; loader requests a shadow update, unmasks the hardware trigger, and waits 200 ms for a diagnostic frame count **before** jumping to XNU (P/probe/display.c:228–255; P/probe/xnu.c:751–755; W/darwin-touch1.txt:1298–1309, 1339–1340). Count advanced 5→17 during that one wait (W/darwin-touch1.txt:1340). The driver's optional beat/beam waits and GPU wait occur before `began` is reset for drawing; its displayed statistic accumulates wall time through drawing and recording, so preemption and recording can contribute (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:1424–1468, 1545–1578). One interval reports 79,142 µs and 3 µs GPU wait, another 18,598 µs; frames arrive much less often than the draw cost alone implies (W/darwin-touch1.txt:28153, 28396). These observations do not prove which fraction is memory bandwidth, filtering, scheduling, or CPU speed.

`hakios/speed.patch` adds opt-in `fb_rowstage=1`: compute scaled output in cached 256-pixel stack tiles and memcpy sequential chunks to the existing framebuffer; unscaled and default paths are unchanged. It preserves the existing per-layer order and filter arithmetic and does not read the scanout for damage. **Guess, not a measured result:** 15–80 ms/frame under comparable load is plausible, including no improvement or regression, because the same full output, interpolation, and scheduling remain; no narrower cost estimate is supported by this log. Test baseline versus `fb_rowstage=1`, also compare existing `fb_filter=0 fb_threads=1` to isolate filtering and helper scheduling (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:156–163, 187–191, 1081, 1188–1205). Check visual output, especially clipped layers and filtered edges. Measure drawing wall and CPU time separately and isolate the copy stage before claiming a win.

A more promising subsequent change is a cached **two-buffer** final-composition shadow: render all layers into one, compare with the previous final image in cached memory, copy changed row spans to WCOMB scanout, and swap shadows only after a complete update. Preserve previous content when layers do not cover the screen, force full invalidation after console or other framebuffer writers, and handle settle redraws, clear, clipping and failed allocations; per-layer damage is not sufficient when layers overlap (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:1403–1420, 1499–1543, 2046–2051). This avoids expensive scanout reads (`fb_diff` explicitly reads scanout) and can reduce writes on mostly static screens, but it still computes the scaled image; full-motion frames may cost more (K/xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp:410, 867–879). A cached scanout plus clean is a separate hardware experiment only after proving compatible aliases and DECON coherency; do not mix it into this patch (K/xnu-src/xnu-8796.121.2/osfmk/console/video_console.c:2856–2879).

## 2. CPUs

`cpus=1` is supplied by the caiman loader default (P/probe/platform_caiman.h:75; W/darwin-touch1.txt:1338). Removing it alone is insufficient: the generated Apple-style tree contains only the boot CPU, with `reg` from MPIDR and logical `cpu-id` 0 (P/probe/xnu.c:504–519). The live Linux DT lists PSCI CPUs with MPIDRs 0x000, 0x100, …, 0x700 (W/caiman-live.dts:3154–3235). The watcher already successfully owns 0x100 (P/probe/platform_caiman.h:74; P/probe/watcher.c:288–296; W/darwin-touch1.txt:1327). Exclude it from XNU's CPU nodes while the watcher runs; do not issue CPU_ON for it or shut it down without redesigning watchdog/return ownership (P/probe/watcher.c:241–283).

Plan: add an opt-in loader mode that emits boot CPU plus distinct logical IDs and physical `reg` values for selected 0x200–0x700 CPUs, removes the single-CPU limit only in that mode, and retains 0x100 for the watcher (P/probe/xnu.c:504–519, 732–739). Generic XNU already calls PSCI CPU_ON and waits for scheduler entry, with cache cleaning for the secondary entry (K/xnu/files/osfmk/arm64/psci_smp.c:144–205). Verify the actual target enables `GENERIC_PSCI_SMP`, the SMC conduit, CPU enumeration conventions, early entry and exit before proposing a loader patch (K/xnu/files/osfmk/arm64/psci_smp.c:51–54, 116–125, 160–205). Linux DT uses `enable-method = "psci"`; it does not require a spin-table `cpu-release-addr` for these nodes (W/caiman-live.dts:3154–3235); determine any additional Apple-tree properties from the actual enumeration code before emitting them. GIC mapping is already supplied by the loader and kernel scans redistributors by MPIDR, then wakes the matching frame (P/probe/xnu.c:392, 524–529; K/xnu/files/osfmk/arm64/gic_v3_irq.c:396–412, 437–457). Verify the advertised redistributor range covers every selected CPU and test SGIs, timers and orderly return (K/xnu/files/osfmk/arm64/gic_v3_irq.c:396–412; K/xnu/files/osfmk/arm64/psci_smp.c:316–355). No SMP patch is included because these platform details have not been established.

## 3. Frequency

The loader writes a constant 1.8 GHz into the generated CPU tree; this is metadata, not evidence of a programmed or measured clock (P/probe/xnu.c:510–516; K/xnu-src/xnu-8796.121.2/pexpert/arm/pe_identify_machine.c:147). The supplied run does not establish the actual bootloader frequencies of any cluster; they remain **unknown**, not assumed to be 1.8 GHz. The live DT describes Exynos ACME CPU domains 0–3, 4–6 and 7, CAL IDs, min/max, resume values and thermal cooling associations (W/caiman-live.dts:3370–3422). It also describes an Exynos DVFS manager on ACPM IPC channel 1 and asynchronous DVFS channel 5 (W/caiman-live.dts:16970–16999), while the probe's PMIC transaction uses ACPM mailbox/SRAM infrastructure and channel 2 (P/probe/touch.c:19–26, 62–63; W/caiman-live.dts:15514–15525). This supports a shared transport, **not** interchangeable PMIC and DVFS messages. The local DT alone does not establish the precise Linux CAL/ACPM rate command, firmware ABI, voltage sequence, clock readback, or actual boot OPP; no safe frequency-raising write can be inferred from it (W/caiman-live.dts:3370–3422, 16970–16999; P/probe/touch.c:62–63).

Next: obtain the matching Google ACME/CAL/ACPM implementation and firmware ABI, identify read-only rate and OPP discovery and dependency/thermal limits, then measure boot rates. Only after that, consider an explicitly enabled bounded OPP request through the verified firmware interface, with timeout and response validation and thermal control. Do not write PMIC voltages or guess a channel payload. The existing kernel cpufreq driver is Qualcomm EPSS/RSC-specific, not evidence of a zuma implementation (K/drivers/power/hakios.cpufreq.c:95, 392).

## Verification and limits

`git apply --check` passed against the existing uncommitted kernel tree. It checks applicability only; it does not compile, run, verify image identity, or establish performance. No loader patch is supplied because the evidence is insufficient for a safe SMP or DVFS change. The staged-copy patch is an experiment rather than a demonstrated fix; the damage and SMP work above remains to be implemented and validated.
