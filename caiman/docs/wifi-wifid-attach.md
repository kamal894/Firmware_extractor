# Caiman Wi-Fi discovery on iOS 16.5 (20F66)

Source paths are relative to `~/caiman-work/hakios-xnu-kernel` unless marked `probe/` (scratchpad `fw/caiman`). “Run 77” refers to `ufslog-77.txt`. Binary instruction addresses are unslid Mach-O addresses from `otool -tvV`. String and data offsets are file offsets in the named executable or dyld subcache.

## 1. How wifid discovers the interface

**configd is required for WiFiManager's discovery path.** In `sysimage/rootfs/usr/sbin/wifid`, `WiFiManagerScheduleWithQueue` calls `SCDynamicStoreCreate` at `0x100067f74`, sets its dispatch queue at `0x100067f90`, and sets a disconnect callback at `0x100067fa4`. Failure at any of the three branches to cleanup at `0x100068754–0x100068804` and skips registration of the Wi-Fi IOKit notification. On success it subscribes to the state interface key and immediately calls its store handler (`0x100067f80–0x100067fb8`, `0x10008c204–0x10008c278`). The handler reads the dictionary at `State:/Network/Interface`, takes its `Interfaces` array, filters names by Wi-Fi media, and passes each candidate to the device-added routine (`0x10008bfe4–0x10008c198`). This also processes subsequent store updates. Run 77 shows failed lookups for `com.apple.SystemConfiguration.configd` from wifid at 4425–4426, 4441–4442 and 4745–4746. The local generated jobs directory lacks `com.apple.configd.plist`.

**The first IOKit match is property-only.** The daemon passes the constant dictionary at file offset `0x234c10` to `IOServiceAddMatchingNotification` at `0x100067ffc`, with notification type `IOServiceMatched`. The one-element outer dictionary's key/value arrays at `0x2349a8/0x2349b0` point to the `IOPropertyMatch` CFString and the one-element dictionary at `0x234be8`. Its key/value arrays at `0x234998/0x2349a0` point to `IO80211InterfaceRole` and `Infrastructure`. Thus the actual dictionary is `{"IOPropertyMatch":{"IO80211InterfaceRole":"Infrastructure"}}` with string key and value. It has no class or provider predicate. `IO80211SkywalkInterface` is in the registration error format at `0x1a73a6`.

The notification is drained immediately at `0x10006800c`. Its handler at `0x10006a8ac` iterates services, reads `IOInterfaceName` (CFString object at `0x21ddb8`, backing string at `0x19c90b`), and runs the same media test as the store handler. The media test at `0x10008cff8–0x10008d0a8` calls ioctl `0xc02c6938` and requires success with `ifm_current & 0xe0 == 0x80` (the 802.11 media type, `xnu-src/xnu-8796.121.2/bsd/sys/sockio.h:136–139`, `bsd/net/if_media.h:262` under the same XNU tree).

**Both paths converge and require the BSD name in the store.** The routine at `0x10008c3a0` checks for a duplicate and requires the requested name in the state's `Interfaces` array before looking up the service (`0x10008c400–0x10008c4d8`). It then calls `IOServiceGetMatchingService` with `{"IOPropertyMatch":{"IOInterfaceName":"en0"}}`, retrying up to 32 times with 10 ms sleeps (`0x10008c4dc–0x10008c578`). It reads the returned service's role and compares it to `Infrastructure` (`0x10008c5c0–0x10008c5f4`) before calling `WiFiDeviceCreate` at `0x10008c61c`. `WiFiDeviceCreate` reads the name, can construct it from string prefix and numeric unit if needed, and requires an IOService-plane parent (`0x100041dcc–0x100041f40`). The daemon calls `Apple80211Open`, `Apple80211BindToInterfaceWithParams`, and then `Apple80211GetPowerState` at `0x100047a8c–0x100047ac4`.

**InterfaceNamer is a related configd dependency.** The BSD list and naming readiness are distinct checks. The 20F66 `/usr/libexec/configd` has a BSD interface-list writer at `0x1000132cc–0x1000133a0` that sets the state interface key with `kSCPropNetInterfaces`. Its built-in InterfaceNamer separately registers a first-match notification for `IONetworkInterface` at `0x100017b10–0x100017b40`. Its strings include `IONetworkStack`, `IOInterfaceNamePrefix`, `IOInterfaceUnit`, `*QUIET*`, and `*TIMEOUT*` (file offsets `0x5f41d–0x5f58b`). The kernel's compatibility shim describes the second dependency explicitly. It provides an openable `IONetworkStackUserClient` so InterfaceNamer can publish readiness under `Plugin:InterfaceNamer`; the source documents that `SCNetworkInterfaceCopyAll` waits for naming readiness or timeout. See `xnu-src/xnu-8796.121.2/iokit/Kernel/MiniIONetworkStack.cpp:1–15,36–45,60–72,84–114` and its startup call at `iokit/Kernel/GenericARMPE.cpp:305` under the same XNU tree. wifid calls `_SCNetworkInterfaceCreateWithIONetworkInterfaceObject` when updating SystemConfiguration after device creation (`0x10008c61c–0x10008c664`). The traced discovery gate reads the BSD-list key, with no direct read of `Plugin:InterfaceNamer` in that gate.

**Device tree and the client framework.** The stock wifid plist's `_LimitLoadToDeviceTree` array contains `wlan` and `marconi-wifi` (decoded with `plutil -p`). The explicit job generator drops the key (`userland/mkjobs.py:267–277`), and the generated `userland/root/LaunchDaemons/com.apple.wifid.plist` lacks it. Run 77 lines 2345 and 3314–3319 show the job on Redwood and the daemon running. wifid does separately look up `wlan` via `IOServiceNameMatching` at `0x10002d85c–0x10002d87c` to read `com.apple.wlan.init_failure` in `__WiFiMetricsManagerGetDeviceInitFailureReason` (`0x10002d8a0–0x10002d990`, property string at `0x19597f`). The traced attachment predicates above have no device-tree-name check.

MobileWiFi's client side is evidenced by the 20F66 cache's MobileWiFi image (`dyld_shared_cache_arm64.15`, Mach-O at `0x3477000`). Its strings include `WiFiManagerClientGetDevice` (`0x34a2c1e`), `WiFiManagerClientDispatchAttachmentEvent` (`0x34a2c5a`), `com.apple.wifi.manager.available` (`0x34a2c83`), `com.apple.wifi.manager` and `__WiFiManagerClientGetOrReconnectServerPort` (`0x34a2cf9/0x34a2d10`), and `__WiFiManagerClientAddDevice` (`0x34a2d74`). These support the client/server split. The actual IOKit discovery and device-added code traced above is in wifid. The complete MobileWiFi client call graph and Settings tap stack were outside the recovered evidence. IO80211 is a separate framework. Its image in subcache `.25` has `IOInterfaceName` at `0x20f5cd2` and the `Falling back to IOCTL path` message at `0x2107ff3`.

**What to look for in a successful run.** The store-handler formats are `Discovered %ld airport Interfaces` and `Now attempting to add AirPort Interface with BSDName %@` (wifid file offsets `0x1ae869/0x1ae88b`, references at `0x10008c110/0x10008c140`). The stronger markers are `__WiFiManagerDeviceAddedCallback: Device manager created. … automatic association state` and `Detected 1 wifi device(s)` (formats at `0x1ae9e3/0x1aea1e`, references at `0x10008ce20/0x10008cec4`). For failure localization, look for `Error creating dynamic store.` (`0x1ae7bb`), `%@ does not exist in dynamic store` (`0x1ae900`), `No Matching Service Found for interface %@` (`0x1ae96d`), and the separate Apple80211 open/bind errors (`0x19d24b/0x19d270`). These logger calls are conditional, so console silence cannot distinguish all branches.

## 2. What HakiosWLAN publishes and what differs from the earlier phone

| Contract | Implementation and evidence |
| --- | --- |
| Infrastructure role and BSD name | `HakiosWLAN` publishes string properties `IO80211InterfaceRole = Infrastructure`, `IOInterfaceName = en0`, `BSD Name = en0`, and `IOInterfaceNamePrefix = en`; 32-bit `OSNumber` values `IOInterfaceType = 6` (IFT_ETHER) and `IOInterfaceUnit = 0` for en0; and boolean `IOBuiltin` and `IOPrimaryInterface`. This meets the two property dictionaries and supplies the name fallback types. `drivers/wifi/hakios.wlan.cpp:151–169`, `drivers/net/hakios.net.c:377,408–411`. |
| Parent and framework access | The child is `HakiosWLAN : IONetworkInterface`; its parent is the synthetic `IO80211Controller : IOEthernetController : IONetworkController : IOService`. The controller carries a six-byte `OSData` `IOMACAddress` and boolean `IOBuiltin`. This supplies a parent for wifid and the hierarchy intended for SystemConfiguration Wi-Fi classification. The child deliberately refuses a user client and logs the first eight requests. `drivers/wifi/hakios.wlan.cpp:13–19,45–93,134–165`. |
| BSD media and attach timing | Once `ifnet_attach` succeeds, the wireless path calls `HakiosWLANStart`. The driver returns 802.11 media through the 32/64-bit `SIOCGIFMEDIA` variants and forwards Apple80211 ioctls. BCM4390 installs station ops after the interface attach and emits the initial power event. `drivers/net/hakios.net.c:215–216,240–251,264–266,395–411`, `drivers/wifi/hakios.bcm4390.c:1004–1023`, `drivers/wifi/hakios.sta.c:162–199`. |
| Registration | `publish` attaches, names, starts and calls `registerService()` on the controller first, then on the child after the child's properties are set. The code logs allocation/attach/start errors, but does not verify matching completion or property setter results. XNU's void `registerService` can return after platform adjustment declines the service, otherwise it enters `startMatching(options)`. `drivers/wifi/hakios.wlan.cpp:96–111,126–170`, `xnu-src/xnu-8796.121.2/iokit/Kernel/IOService.cpp:1010–1037,1066`. |

Run 77 lines 3823–3828 confirm a successful version query, BSD interface attach, station power event and BCM4390 completion. There is no `HakiosWLAN` error or user-client request and no `net: en0 is asked … by wifid` marker from `hakios.net.c:222–230` in the captured log. The latter trace has a budget of 80 calls. This is consistent with no discovery query reaching the interface; it does not certify registry visibility. Launchd reports wifid running at 3314–3319, before those attach lines; wifid's later initialization and lookup messages occur after attach (4425–4442, 4743–4764). There is no timestamp for the matching call itself. A registered service can be consumed from the initial iterator or a subsequent notification, and the store subscription provides another route once the name enters the store.

**Caiman's loader source emits no `wlan` node.** `probe/xnu.c:424–627` constructs the tree, with `mac-address-wifi0` under `chosen` at line 507 and explicit `arm-io` children at 601–619. The identity arrays are applied as properties of explicitly created nodes (450–455, 556–569). Run 77 line 2065 confirms an identity header was compiled in. The referenced `probe/identity.h` is absent in the current scratchpad source. The repository copy `xnuloader/identity.h:28` has a `wifi-chipset` property, and `xnuloader/mkidentity.py:92–102` emits property arrays. Neither a chipset property nor the chosen MAC property adds a node. The shim attempts to find a service named `wlan`, seeds its six-byte `local-mac-address` if found, and otherwise publishes under the platform (`drivers/wifi/hakios.wlan.cpp:118–143`). Its comments at 21–27 document MobileGestalt's separate MAC lookup and delay. The provider choice does not change either traced wifid property match.

**The earlier working report describes the WCN6750 phone path.** `userland/build.sh:116–124` says the radio with `wifi=1` showed Wi-Fi on, the joined network, and nearby networks, with joins initiated in Settings still unfinished at that point. It separately describes radio-less QEMU doing country-code work, consistent with QEMU's failed wifid configd lookups (`logs/qemu.log:1290,1589`). The phone's `wifi=1` brings up WCN6750 (`docs/devices/redwood.md:30`), and its early attach path publishes the interface before the radio finishes startup (`drivers/wifi/hakios.lx.c:330–347`). A separate earlier phone test describes “every stock job on demand” and configd configuring en0 (`drivers/wifi/hakios.wifi.c:3362–3367`; see also `userland/rc.jobs.ssh:2–3`). This establishes a working configd in the documented phone networking configuration. The exact earlier launch-job set for the Settings observation is unverified. The default list in the current `userland/build.sh:106–126` does not explicitly select configd. The older HackiOS loader source also has no explicit `wlan` node in its DT construction (`xnuloader/loader.c:3220–3440`), so there is no evidence here that the successful phone test had such a node.

Caiman already runs the same `com.hakios.wifi` job (Run 77 2328, 3428–3432, 3834–3842; `userland/com.hakios.wifi.plist:5–15`). The run omits `wifi=1` (2074), so `net_test wifi` returns at its boot-arg check (`userland/src/net_test.m:384–397`). When enabled, the job waits for en0 and lets configd configure it if a named network service exists, then falls back to requesting DHCP (`net_test.m:398–429`). The kernel tries BCM4390 first and returns upon a valid start before parsing the legacy radio's `wifi` knob (`drivers/wifi/hakios.wifi.c:4320–4339`, `drivers/wifi/hakios.bcm4390.c:1026–1035`). Run 77 already has the BCM4390 handoff and one-second delay (2074, 2210–2211).

## 3. Minimal changes in order of likelihood

1. **Explicitly add the stock configd job to Redwood and verify the store before changing the driver.** For the next build, add `com.apple.configd` to the named `DARWIN_JOBS` list at `userland/build.sh:106–126` (equivalently append it to the existing list supplied at build time). `build.sh:460–468` and `mkjobs.py:267–277` copy it to `/redwood/LaunchDaemons/com.apple.configd.plist`. Prefer explicit selection so its stock KeepAlive survives the on-demand filtering at `mkjobs.py:290–304`. The stock plist declares `com.apple.SystemConfiguration.configd` and runs `/usr/libexec/configd`. The System manifest already includes the executable and InterfaceNamer bundle metadata (`sysimage/system.manifest:45223–45230,47467`); InterfaceNamer code is built into the executable as shown above. For validation, enable console logging for both jobs via `OSLOG="com.apple.backboardd com.apple.configd com.apple.wifid"` (`build.sh:468`, `mkjobs.py:270–275`). Check that the endpoint resolves, `State:/Network/Interface` contains en0, `Plugin:InterfaceNamer` advances, and wifid reaches the device-manager and power markers. If launch-domain/session restrictions keep configd from appearing, inspect its stock conditional `LimitLoadToSessionType` and the actual launchd domain before altering the plist. If wifid attempted initialization before configd became usable and stayed detached, a later start with the store already ready would distinguish startup ordering from a registry mismatch. **Guess:** this restoration may also unblock the Settings pane. The daemon's configd gate is verified statically; the tap outcome is unverified.
2. **If configd is running and discovery still stops, instrument the first unmet gate.** Check the BSD list and media ioctl, then the two matching dictionaries from section 1. For a missing match, add a diagnostic at `hakios.wlan.cpp:143–169` that checks each relevant property setter and records the provider, class and properties, then verify the published child using the role and name dictionaries. When troubleshooting InterfaceNamer, look for the existing `MiniIONetworkStack: opened by configd` marker (`MiniIONetworkStack.cpp:60–72`) and registry busy state before adding any naming code. **Guess:** if a repeatable publication race remains after restoring configd, test `service->registerService(kIOServiceSynchronous)` in `publish` at `hakios.wlan.cpp:110`, only if the caller's context can block. The initial iterator and callbacks already account for early and late publication, so evidence of a registration/timing problem should precede that change. The disassembly provides no basis for renaming the class to `IO80211SkywalkInterface`.
3. **Add a minimal `wlan` node only for a demonstrated provider/MAC problem.** A loader experiment at `probe/xnu.c:601–619` can add an `arm-io` child using `dt_begin(&w, "wlan")` and `dt_end(&w)`. Confirm it is published as a matchable IOService provider and receives the real six-byte MAC from `hakios.wlan.cpp:134–143`. **Guess:** this can fix MobileGestalt MAC lookup or `wlan`-specific metrics and provider behavior, but it ranks below the verified configd gate. Preserve the generated wifid job that already launches. A stock plist launch-gate experiment would test a different path.
4. **Keep `wifi=1` and the other missing jobs out of the first comparison.** The helper's switch controls its DHCP fallback (`net_test.m:374–429`); it does not populate WiFiManager's discovery list or launch configd. The PPM message at Run 77 4743–4744 is the ApplePPM lookup described in `wifi-ios-userland.md` section “Interface discovery and PPM.” The other missing endpoints are visible at Run 77 4413–4428, 4435–4436, 4653–4654 and 4930–4931, with no traced dependency on them in the initial match. If wifid detects a device and the pane still hangs, inspect the Preferences watchdog separately. Run 77 9118–9127 and 10301–10308 correlate the client termination callbacks with SpringBoard exits for PIDs 34 and 36 (`0x8BADF00D`, failed to terminate gracefully). Those lines provide no backtrace or tap-time cause. The Settings row and controller are documented in `wifi-ios-userland.md` section “Settings and launch jobs.”

## Summary

The 20F66 daemon needs a working configd dynamic-store session and an en0 entry in the BSD interface list even when the IOKit notification finds HakiosWLAN. The shim's role, name, media and parent agree with the discovery code on paper. Run 77 proves BSD attach and shows failed configd lookups; successful registry matching and the cause of the Settings watchdog remain unverified. Adding the existing configd job is the smallest change supported by the disassembly and run log.
